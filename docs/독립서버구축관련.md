# 이미지 분석 AI 독립 서버 구축 검토

- 작성일: 2026-09-14
- 배경: 현재 전주번호찰 선로 정보 추출은 Gemini/Claude/OpenAI 등 유료 API를 호출해서 처리 중. Hugging Face의 오픈소스 AI 모델을 직접 가져와 자체 서버에 설치해서 분석하는 것이 가능한지, 가능하다면 어떤 모델이 적합한지, 그리고 대량(50~100장) 배치 처리 시 유료 API(Gemini Flash)로도 문제가 없는지에 대한 검토 내용.

## 1. Hugging Face 모델을 직접 가져와 자체 서버에서 돌리는 것이 가능한가?

**기술적으로는 가능하지만, 현재 이 프로젝트의 배포 구조(Vercel Serverless Functions)로는 불가능하다.**

- Vercel Serverless Function은 GPU가 없고, 메모리(약 1~3GB)·실행시간(플랜에 따라 짧게는 10초 안팎, 최대 수십~수백 초) 제한이 있어서 비전-언어 모델(보통 수 GB~수십 GB 크기) 추론을 돌릴 수 없다.
- 따라서 **별도의 GPU 서버**(RunPod, Vast.ai, Lambda Labs, 자체 보유 GPU 머신 등)에 모델을 올리고, 추론 API를 하나 만들어서 이 앱의 `providers/` 디렉터리에 있는 `gemini.ts`, `claude.ts`, `openai.ts`처럼 "self-hosted" provider를 하나 추가해 호출하는 구조가 되어야 한다.
- 즉, "Vercel에 모델을 얹는다"가 아니라 "Vercel 프론트엔드/백엔드 + 별도 GPU 서버(추론 전용)"의 2단 구조가 된다.

## 2. 추천 모델

이 앱이 필요로 하는 작업은 단순 OCR이 아니라, **번호판의 글자를 읽고 + 어느 텍스트가 선로명/전산화번호/선로번호인지 구조적으로 판단해서 JSON으로 응답하는 것**(`providers/prompt.ts`의 `EXTRACTION_INSTRUCTION` 참고, bounding box 좌표까지 함께 요구)이다. 따라서 순수 OCR 모델보다는 **비전-언어 모델(VLM)** 이 적합하다.

| 모델 | 특징 |
|---|---|
| **Qwen2.5-VL-7B-Instruct** (1순위 추천) | 한글 포함 다국어 OCR 성능 우수, 구조화 JSON 출력 지시를 잘 따름, vLLM/Ollama 등으로 셀프호스팅 생태계가 성숙. 24GB급 GPU 1장이면 fp16으로 충분 |
| Qwen2.5-VL-3B-Instruct | 동일 계열의 경량판. 8~12GB급 GPU로도 구동 가능하나 정확도는 7B보다 다소 낮음 |
| InternVL2-8B | Qwen2.5-VL의 대안. OCR/문서 이해 벤치마크에서 상위권 |

**저사양/CPU만 있는 경우 대안**: PaddleOCR(한글 지원, CPU로도 실용적인 속도)로 텍스트만 추출하고, 그 결과를 경량 LLM(Qwen2.5-7B-Instruct 등)에 넣어 필드로 구조화하는 2단계 파이프라인. 다만 번호판 bounding box 검출이나 "이 숫자가 전산화번호인지 선로번호인지" 판단을 직접 코드로 구현해야 해서 개발 난이도는 더 높다.

## 3. 비용 관점에서 참고할 점

- Gemini Flash 계열은 이미지 1장당 비용이 매우 저렴(대략 건당 1원 미만~수 원 수준)해서, 사용량이 아주 많지 않다면 **GPU 서버를 24시간 띄워두는 비용이 API 비용보다 더 클 수 있다.**
- 콜드스타트 방식(RunPod Serverless 등, 사용하지 않을 때는 종료)을 쓰면 유휴 시 비용은 0이지만, 요청마다 모델 로딩으로 수십 초 지연이 생겨 UX가 나빠질 수 있다.
- 셀프호스팅은 "비용 절감"보다는 **API 키 의존 제거, 데이터를 외부로 보내지 않는 것** 등이 주 목적일 때 더 합리적인 선택이다. 순수 비용만 보면 현재 규모에서는 유료 API 유지가 더 저렴할 가능성이 높다.

## 4. 대량 배치(50~100장) 업로드 시 Gemini Flash로 문제없는가?

### 검토 당시 문제점 (수정 전)

당시 코드는 동시 요청 수 제한이 전혀 없어서, 50~100장을 업로드하면 **거의 동시에 50~100개의 요청**이 `/api/extract` → Gemini API로 나가는 구조였다.

1. **Gemini API 분당 요청수(RPM) 한도 초과 가능성** — 무료 티어 키는 분당 요청 한도가 매우 낮아(대략 10~15RPM 수준) 100장을 한번에 올리면 대부분 429(rate limit)로 실패할 가능성이 컸다. 유료(종량제) 키는 한도가 훨씬 높아 100건 정도의 순간 버스트는 대체로 버티지만 여유는 크지 않았다.
2. **자동 재시도 부재** — 429/503을 감지해 한국어 에러 메시지로 바꿔주기는 했지만 자동 재시도는 없었다. 실패 시 사용자가 수동으로 재시도해야 했고, "전체 재시도"조차 전부 동시에 재요청하는 구조라 같은 문제가 반복될 수 있었다.
3. **Vercel 서버리스 함수 타임아웃 위험** — 요청이 몰리면 일부 응답이 지연되어 함수 실행시간 제한에 걸릴 위험이 있었다.

### 적용한 해결책 (2026-09-14 배포 반영)

- **동시 처리 개수 제한**: `src/lib/asyncQueue.ts`의 워커풀로 최대 5개씩만 동시에 API를 호출하도록 큐 처리. 업로드 직후 일괄 분석과 "전체 재시도" 양쪽에 적용(`src/App.tsx`).
- **자동 재시도**: 429(요청 한도 초과)·500/502/503/504(서버 오류·과부하)만 재시도 대상으로 삼아 최대 3회(1.5초, 3초 + 약간의 랜덤 지연) 자동 재시도. 401(API 키 오류) 등은 재시도해도 소용없으므로 바로 실패 처리하고 기존 수동 재시도 버튼으로 넘김.

이 두 가지를 적용한 뒤로는 Gemini Flash(특히 유료 키 기준)로도 50~100장 배치 처리에 문제없이 대응할 수 있다고 판단. 모델을 교체하거나 별도 서버를 구축하는 것보다 훨씬 간단하고 효과적인 해결책이었다.

## 5. 결론

- 지금 이 프로젝트 규모(수동 업로드, 세션당 수십~백 장 단위)에서는 **Gemini Flash + 클라이언트 큐/재시도**로 충분히 안정적으로 대응 가능하다.
- Hugging Face 모델 셀프호스팅은 기술적으로 가능하지만, 별도 GPU 서버 구축·운영 부담이 크고 비용 이점도 불확실하다. 아래와 같은 경우에만 재검토할 가치가 있다:
  - 이미지 분석 물량이 매우 커져서(예: 하루 수만 장 이상) API 종량제 비용이 실제로 부담되는 시점
  - 사진 데이터를 외부 API로 보내는 것 자체가 정책/보안상 불가능해지는 경우
  - 오프라인/폐쇄망 환경에서 동작해야 하는 경우
- 재검토 시 권장 경로: Qwen2.5-VL-7B-Instruct를 vLLM으로 서빙 → `providers/`에 self-hosted provider 추가 → RunPod 등 GPU 서버에 배포.
