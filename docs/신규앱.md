# 신규앱 — 전지작업 현장 사진 앱 (별도 프로젝트)

> ⚠️ **2026-09-26 업데이트**: 이 문서 작성 이후 WattLineWeb에 DB와 로그인이 도입되었다. 아래 "DB 없음", "로그인 없음" 서술은 과거 기록이다.
> - Supabase `WattLine` DB에 `companies`/`app_users`/`workplaces`/`workplace_workers` 테이블을 추가했다. 작업 건(작업장) 단위로 사진을 묶을 수 있다.
> - `pruning-photos` 버킷은 `{workplace_id}/파일명` 폴더 구조로 바뀌었다. `POST /api/pruning`에는 `workplaceId`가 필수다.
> - 모바일 앱(WattLineApp) 사진은 `photo_uploads.workplace_id`로 작업장에 연결한다. **WattLineApp이 업로드 시 `workplace_id`를 넣도록 수정해야 한다.**
> - 상세: `docs/2026-09-26-admin-schema.md`

> 작성일: 2026-09-16
> 목적: 배전선로 수목전지 작업 전/후 현장 사진을 촬영·업로드하는 모바일 전용 앱을 **별도 프로젝트**로 새로 만든다.
> 이 문서는 (1) 현재 `WattLineWeb` 프로젝트에서 신규앱 개발 시 알아야 할 정보, (2) 신규앱이 갖춰야 할 요건을 정리한다.

## 0. 왜 별도 프로젝트인가 (결정 배경)

- `WattLineWeb`은 **데스크탑 전용**으로 유지하기로 결정함. 신규앱은 현장 작업자가 스마트폰으로 쓰는 **모바일 전용** 앱이라 UI/반응형 전략, 카메라 접근, 오프라인 대응 등 요구사항이 완전히 다름.
- 연동은 코드 공유가 아니라 **API/스토리지 레벨**로 충분하다고 판단함 (아래 2장 참고). 같은 리포에 넣으면 Vercel 빌드 설정(entry, `/api` 라우팅)이 얽힐 위험만 있고 실익이 없음.
- 두 앱이 타입(`PruningRecord` 등)을 공유하고 싶어지면 그때 가서 모노레포(workspaces)나 공용 npm 패키지를 고려. 앱이 2개뿐인 지금 단계에서는 과한 구조.

## 2. 사진이 실제로 어떻게 저장되는가 (신규앱이 알아야 할 핵심)

### 2.1 저장 방식 — Supabase Storage뿐, DB 없음

`providers/handlePruningRequest.ts`가 Supabase Storage `list`/`upload`/`createSignedUrl`/`remove`를 감싼 전부다. 사진은 `pruning-photos` 버킷 루트에 `{timestamp}-{랜덤6자리}-{원본파일명}` 형태의 pathname으로 저장된다. 버킷이 private이라 조회 시마다 signed URL(유효시간 6시간)을 새로 발급한다. **사진 사이의 관계(어느 작업 건의 전/후 사진인지, 촬영자, 위치 등)를 담는 구조화된 메타데이터는 전혀 없다.**

- `GET /api/pruning` → `{ photos: [{ url, pathname, uploadedAt }, ...] }` (버킷에 있는 걸 그대로 나열, 최신순, url은 매번 새로 발급되는 signed URL)
- `POST /api/pruning` (body: `{ fileName, mimeType, dataUrl }`, `dataUrl`은 `data:image/...;base64,...` 형식) → 업로드 후 `{ url, pathname, uploadedAt }` 반환
- `DELETE /api/pruning` (body: `{ pathname }`) → 해당 파일 삭제 (Blob 시절엔 `url`로 식별했으나 signed URL은 매번 바뀌므로 안정적인 `pathname`으로 식별하도록 바뀜)

### 2.2 화면에서 보이는 "전주번호/수목종류/작업내용" 등은 서버에 저장되지 않는다

`PruningWork.tsx`의 `PruningRecord`(→ `src/types.ts`)는 **브라우저 메모리에만 존재**하는 상태다. AI 분석 결과, 참고사진 2장(`extraPhotoUrls`) 연결, 사용자가 표에서 직접 수정한 값 모두 새로고침하면 사라진다. 새로고침 시 남는 건 오직 `GET /api/pruning`이 돌려주는 **URL 목록**뿐이다 (이미 알려진 제약이며, `HANDOFF.md`에도 "AI 분석 결과는 새로고침하면 사라짐" — 당시 "DB 도입은 보류, 일단 Vercel Blob으로" 결정한 바 있음).

→ **신규앱이 "이 사진은 A 작업 건의 전(前) 사진, 이 사진은 후(後) 사진"처럼 관계를 남기고 싶다면, 지금 WattLineWeb 쪽엔 그걸 받아줄 자리가 없다.** 아래 3장의 미해결 사항 참고.

(참고: WattLine 모바일 앱은 이미 별도의 Supabase DB `photo_uploads` 테이블 + `photos` 버킷으로 작업장/카테고리별 메타데이터를 관리 중이며, WattLineWeb은 `/api/wattline-db`로 이를 읽어와 전지작업 화면에 표시한다. 자세한 내용은 `docs/HANDOFF_from_WattLineApp.md` 8장 참고. 다만 이건 신규앱이 아니라 WattLine 앱 쪽 스키마이며, WattLineWeb 자체의 업로드 사진(`pruning-photos` 버킷)과는 별개다.)

### 2.3 업로드 전 클라이언트 압축 관례

`src/lib/resizeImage.ts`: 업로드 전 브라우저에서 긴 변 1600px로 리사이즈 + JPEG 90% 재압축 후 `POST /api/pruning`으로 보낸다. 이유는 두 가지: (1) Vercel Serverless 요청 본문 제한(4.5MB) 회피, (2) AI 비전 API가 내부적으로 약 1500~1600px로 처리하므로 그 이상 고해상도는 용량만 커지고 이득이 없음. **신규앱도 같은 관례(1600px, JPEG 90%)를 따르는 걸 권장** — 특히 현장 사진은 원본이 스마트폰 고해상도라 그대로 올리면 용량 문제가 커짐.

## 3. 연동 방식 — 두 가지 선택지

### 옵션 A. 신규앱이 같은 Supabase Storage 버킷에 직접 업로드
`@supabase/supabase-js`의 `storage.from('pruning-photos').upload()`를 신규앱 서버(또는 서버리스 함수)에서 직접 호출. 단, `SUPABASE_URL`/`SUPABASE_SECRET_KEY`를 신규앱 쪽 환경변수로도 가지고 있어야 함 → 민감정보를 두 프로젝트에 나눠 관리해야 하는 부담. (참고: 이 값은 WattLine 앱도 이미 같은 Supabase 프로젝트에 대해 갖고 있으므로, 신규앱이 WattLine 앱과 같은 코드베이스/팀이라면 부담이 크지 않을 수 있음)

### 옵션 B. 신규앱이 WattLineWeb의 기존 `/api/pruning` (POST)를 그대로 호출 — **권장**
신규앱은 키를 몰라도 되고, WattLineWeb 서버가 대신 Supabase Storage에 저장한다. WattLineWeb 쪽에 CORS 허용 설정만 추가하면 됨 (`api/pruning.ts`는 현재 CORS 헤더가 없어 보임 — 신규앱 도메인에서 호출하려면 이 부분 확인/추가 필요).

**주의**: 두 옵션 다 지금 구조 그대로는 "전/후 사진 묶음"이라는 개념을 서버가 이해하지 못한다. `POST /api/pruning`은 파일 하나를 Supabase Storage에 저장하고 signed URL만 돌려줄 뿐, 그 URL들을 하나의 작업 건으로 묶는 것은 여전히 프론트엔드(브라우저 메모리) 몫이다.

## 4. 신규앱(현장 사진 앱)이 갖춰야 할 것

### 4.1 촬영/업로드 핵심 기능
- 카메라 직접 촬영 (모바일 브라우저 `<input capture>` 또는 네이티브 카메라 API) + 갤러리에서 선택 업로드 둘 다 지원
- **전(前)/후(後) 사진 페어링 UI**: 같은 작업 건에 대해 전지 작업 전/후 사진을 짝지어 촬영·확인할 수 있어야 함 (이게 이 앱의 핵심 존재 이유)
- 업로드 전 클라이언트 압축 (2.3절 관례: 긴 변 1600px, JPEG 90% 권장 — 현장에서는 데이터 사용량/전송 속도 문제도 있으므로 더 낮춰도 됨)
- 업로드 진행률/실패 표시, 실패 시 재시도 (기존 프로젝트의 `runWithConcurrency` + 429/5xx 자동 재시도 패턴 참고 가능: `src/lib/asyncQueue.ts`, `PruningWork.tsx`의 `requestPruningExtractionWithRetry`)

### 4.2 현장 특화 요건
- **오프라인 대응**: 현장은 전파가 약할 수 있음. 촬영은 오프라인에서도 가능해야 하고, 네트워크가 잡히면 로컬 큐에 쌓인 사진을 자동 업로드해야 함 (PWA + IndexedDB, 또는 네이티브 앱이면 로컬 파일 큐)
- 작업 메타데이터 입력: 전주번호(시작/끝), 위치, 작업일시, 작업자 — 최소한 어떤 현장 건인지 사람이 구분할 수 있는 정보
- 가능하면 촬영 시점 GPS 좌표 자동 태깅 (전주 위치 확인용, 위 [수목전지 기초] 화면에서도 다루는 "이격거리 확인" 용도로 유용할 수 있음)
- 사진에 EXIF 위치/시간 보존 여부는 결정 필요 (업로드 전 리사이즈 시 EXIF가 날아갈 수 있음 — 필요하면 별도 필드로 좌표를 저장)

### 4.3 WattLineWeb와의 연동 요건
- 업로드 API는 3장의 옵션 B(`POST /api/pruning` 호출)를 기본으로 하되, WattLineWeb 쪽 CORS 설정이 선행되어야 함
- 신규앱에서 올린 사진과 WattLineWeb에서 올린 사진을 구분하고 싶다면 `fileName`에 접두어를 붙이는 정도의 최소 규약이라도 정해둘 것 (예: `field-{작업건ID}-before-...`, `field-{작업건ID}-after-...`)
- WattLineWeb의 "전지작업" 화면에서 신규앱이 올린 사진을 자동으로 인식해 전/후로 묶어 보여주려면, 결국 아래 5장의 DB 도입이 필요함. 그 전까지는 WattLineWeb 쪽에서 사람이 수동으로 매칭(현재 상세보기의 "참고사진 2장 추가" 기능과 유사)하는 방식으로 임시 운용 가능

## 5. 미해결 사항 (설계 전 결정 필요)

- [x] **전/후 사진 그룹핑을 위한 실제 DB 도입 여부** (2026-09-26 작업장 테이블 도입, 사진은 작업장 단위로 묶임. 전/후 구분은 WattLineApp의 `category`로 함): 2026-09-14 당시엔 "일단 Blob으로 충분, DB는 보류" 결정이었고 2026-09-18에 저장소만 Supabase Storage로 옮겼을 뿐 DB(Postgres 테이블)는 아직 도입 안 함. 신규앱이 생기면서 "어느 사진이 어느 작업 건의 전/후 사진인지"가 핵심 요구사항이 되므로, WattLine 앱의 `photo_uploads` 테이블처럼 Postgres 테이블 도입을 재검토할 필요가 있음
